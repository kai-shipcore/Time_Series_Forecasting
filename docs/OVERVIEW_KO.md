# 개요

진입점 문서입니다. 무엇을 구축했는지, 각 구성 요소가 어떻게 연결되는지, 정확도를 어떻게 측정하는지, 그리고 그 결과를 다룹니다.

| 문서 | 다루는 내용 |
|---|---|
| `MODEL_KO.md` | 모델 아키텍처, 피처, 변경 방법 |
| `MODEL_PRIMER_KO.md` | 동일한 내용을 ML 배경 지식 없이 설명 |
| `DATA_AND_PIPELINE_KO.md` | 데이터 소스와 주간 작업 |
| `SCREENS_KO.md` | 두 개의 UI 화면과 해당 엔드포인트 |
| `DEPLOYMENT_KO.md` | 서버 구성, 로컬 개발, 런북 |
| `FUTURE_IMPROVEMENTS_KO.md` | 미해결 작업, 차단 요인별 분류 |

세 개의 참조 파일이 전체 기록을 보유하며, 이 문서가 덜 구체적인 부분에서는 그 파일들이 우선합니다.

- `ML_FORECAST_DESIGN.md`: 근거를 포함한 모든 실험과 기각 사례를 포함한 결정 로그
- `WORKLOG.md`: 수행한 작업의 일자별 기록
- `BACKLOG.md`: 항목화된 기지의 작업

## 1. 문제

차량용 시트 커버 및 액세서리 활성 SKU 3,525개입니다. 구매 부서는 다가오는 분기에 대해 SKU별 주간 수량 수요 추정치를 필요로 합니다.

기존 시스템인 **V1**은 `src/v1.py`에 있는 스프레드시트 수식입니다. 7, 15, 30, 60, 90일 구간의 판매 속도에 수작업으로 설정한 월별 계절 계수를 곱합니다. 두 가지 구조적 한계가 있습니다.

1. 후행 평균은 변화를 미리 반영할 수 없어, 상승 국면은 과소 예측하고 하락 국면은 과대 예측합니다
2. 오차가 크고 계절에 따라 부호가 뒤집히므로 어떤 보정으로도 해결되지 않습니다

산출물은 SKU별 13주 선행 주간 수량 예측이며, Demand Pilot으로 게시되어 Action List가 이를 권장 발주 수량으로 변환합니다.

## 2. 시스템 구성 요소

저장소 두 개, 프로세스 두 개, 데이터베이스 하나입니다.

| 저장소 | 스택 | 역할 |
|---|---|---|
| `Time_Series_Forecasting` | Python, FastAPI | 모델, 주간 파이프라인, 그리고 예측과 계획 계산을 제공하는 API. 포트 8000의 서비스이며 주간 cron으로도 실행됩니다. PostgreSQL을 직접 읽고 씁니다 |
| `Commerce_Integration` | TypeScript, Next.js 16 | Action List와 Forecast Validation 화면을 호스팅합니다. 계획 수치는 Python에서 계산되어 `/api/planning/*` 아래의 얇은 핸들러를 통해 프록시됩니다 |

**근거.** 이 분리는 발주 수식을 하나의 구현으로 유지합니다.

```
shipcore.fc_velocity_link_snapshot_forecast   (order lines, source of truth)
        │  weekly pipeline: scripts/ml_prepare_data.py
        ▼
data/processed/sales_clean.parquet            (one row per SKU per week)
data/processed/sku_profiles.csv               (segment labels per SKU)
        │  LightGBM v11
        ▼
shipcore.ml_forward_forecasts                 (13 weeks ahead, per SKU)
shipcore.ml_forecast_history                  (every forecast served)
        │  src/planning/calc.py + live inventory
        ▼
FastAPI  /planning/action-list, /planning/validation
        │  Next.js proxy, src/lib/planning-api.ts
        ▼
Action List and Forecast Validation screens
```

## 3. 예측 범위

SKU는 학습 시점에 수요 패턴에 따라 분류됩니다. 개수는 고정된 snapshot `2026-08-03-v2` 기준입니다.

| 분류 | 의미 | SKU 수 |
|---|---|---|
| smooth | 모델링이 가능할 만큼 규칙적 | 340 |
| intermittent | 대부분의 주에 판매량이 0 | 3,185 |
| | **합계** | **3,525** |

smooth SKU는 카탈로그의 9.6%이지만 기록된 전체 수량의 78.6%를 차지하며, 후행 1년 기준으로는 75.8%입니다.

**근거.** 대부분의 주가 0일 때 주당 기대 수량은 의미가 없습니다. intermittent SKU에는 예측이 제공되지 않으며, Action List는 이를 다른 기준으로 표시합니다 (`SCREENS_KO.md` §2.9).

smooth SKU는 확보된 이력에 따라 다시 나뉩니다.

| 세그먼트 | 임계값 | SKU 수 |
|---|---|---|
| smooth/short | 활성 판매 50주 미만 | 247 |
| smooth/long | 50주 이상 | 93 |

`long`은 `medium`(50주에서 104주, 40 SKU)과 `full`(104주 이상, 53 SKU)을 합친 것입니다. 레이블은 매주 다시 계산되므로 코드 변경 없이 SKU가 예측 대상에 들어오거나 빠집니다.

주의: 주간 갱신 한 번에 smooth 모집단이 15 SKU만큼 이동했습니다. 카탈로그 개수는 근사치이며 시점에 종속됩니다. 평가 개수는 정확하며, 이는 snapshot의 속성입니다.

## 4. 구축한 내용

### 운영 모델: LightGBM v11

전체 SKU를 함께 학습한 그래디언트 부스팅 트리로, 각 SKU의 최근 수준에 대한 **수요 배수**를 예측합니다. 계절성은 적합 전에 나누어 제거하고 이후 다시 곱합니다. short SKU는 전체 smooth SKU로 학습한 모델을, long SKU는 long SKU만으로 학습한 모델을 사용합니다.

**근거.** 아무것도 학습하지 못한 모델은 1.0을 예측하여 단순 12주 이동 평균을 재현합니다. 그 평균이 하한선, 즉 **구조적 베이스라인**입니다. 그 위의 정확도는 모델에 귀속됩니다. 아키텍처는 `MODEL_KO.md`에 있습니다.

### 퇴역한 프로토타입: statsforecast

1단계는 교차 검증으로 선택한 SKU별 AutoARIMA, AutoETS, 이동 평균이었습니다. 2026-08-13에 퇴역했습니다. 코드는 `src/legacy/`, `api/legacy/`, `scripts/legacy/` 아래에 남아 있으며 라우터는 마운트되어 있지 않습니다.

이는 여전히 정확도 기준선이며, 성공 기준은 세그먼트별로 이를 능가하는 것이었습니다.

같은 시점에 함께 제거된 항목입니다.

| 제거 항목 | 기존 위치 |
|---|---|
| Demand Forecast 페이지 | `/planning/demand-forecast` |
| SKU Planning의 Demand Forecast 탭 | `/planning/sku-forecasts/[sku]?tab=forecast` |
| Next.js 프록시 라우트 14개 | `/api/forecast/*` |

`?tab=forecast`는 여전히 해석되며 Sales Analysis로 연결됩니다. 서비스 중인 모델의 SKU별 화면은 `/planning/action-list/[sku]`입니다.

## 5. 정확도 측정

### 지표

**세그먼트별 pooled WAPE.** SKU 전체의 절대 오차를 합산하고 실적 합계로 나눕니다. 값이 낮을수록 좋습니다. 0.20은 해당 세그먼트가 판매한 수량의 20%만큼 예측이 빗나갔음을 뜻합니다.

- pooled 방식은 물량에 따라 SKU에 가중치를 두어 오차가 유발하는 비용과 일치시킵니다
- 부호가 있는 지표인 편향을 함께 보고합니다. WAPE가 같아도 오차 방향이 서로 반대일 수 있습니다
- 채점은 SKU별 10주 합계를 대상으로 합니다. 재고는 지평 단위로 발주되기 때문입니다

### 구간

rolling-origin 구간이 4개이며, 각각 학습 컷오프 이후 데이터로 채점됩니다. 세 개의 개발 구간은 세 가지 계절 국면에 걸쳐 있습니다.

| 구간 | 컷오프 | 테스트 기간 | 역할 |
|---|---|---|---|
| Oct-Dec 2025 | 2025-10-06 | 2025-10-13 부터 2025-12-15 | 개발, Q4 성수기 |
| Dec-Feb | 2025-12-15 | 2025-12-22 부터 2026-02-23 | 개발, 연휴 이후 저점 |
| Mar-May 2026 | 2026-02-23 | 2026-03-02 부터 2026-05-04 | 개발, 봄철 |
| 최종 테스트 | 2026-05-04 | 2026-05-11 부터 2026-07-13 | 격리됨, 1회 사용 |

### 채택 기준

변경은 다음 조건을 모두 충족할 때만 채택됩니다.

1. 세 개의 개발 구간 전부에서 같은 방향으로 정확도를 개선하고,
2. 세 구간 평균에서 최소 0.01 WAPE를 개선합니다

단일 구간에서 0.02 미만의 차이는 결론을 내릴 수 없습니다. 부트스트랩 재표집은 단일 구간의 잡음을 ±0.011에서 ±0.014로 추정합니다.

통과 기준은 실험 실행 전에 버전 로그에 기록됩니다. 채택과 기각 모두 v0부터 v18까지 기록되어 있습니다.

### 두 개의 고정값

- `ML_FINAL_TEST_CUTOFF`는 각 구간이 포함하는 주를 고정합니다
- `ML_DATA_SNAPSHOT`은 해당 주 안의 값을 고정합니다. 주간 갱신 시 지연 주문이 등록되면서 최근 실적이 수정되기 때문입니다

주의: 둘 중 어느 하나라도 앞으로 옮기면 기록된 모든 수치의 기준이 다시 설정됩니다. 하나를 옮겼다고 해서 다른 하나도 함께 옮겨진 것은 아닙니다.

## 7. 명시된 한계

전체 목록은 `ML_FORECAST_DESIGN.md` §2.2와 `MODEL_KO.md` §6에 있습니다.

- **2년치 데이터.** 모든 계절 관련 결과는 각 계절에 대한 한 번 또는 두 번의 관측에 근거합니다
- **4개 구간은 독립 표본이 아닙니다.** 학습 세트가 크게 겹치며, 계절에 걸친 견고성을 시험합니다
- **long 모델은 약 54개 SKU에 의존하며**, 그중 23개는 서로 상관된 `CC-CN-03`/`CC-CP-03` 변형입니다. 따라서 신뢰 구간이 신뢰도를 과대 표현합니다
- **평가 지평은 10주이지만 운영은 13주를 제공합니다.** 11주에서 13주는 어떤 구간에서도 채점되지 않으므로 모든 수치는 하한값입니다
- **적격성 판정에 미래 정보가 사용됩니다.** 채점 대상 SKU가 부분적으로 컷오프 이후 데이터로 선정되어, 정량화하기 어려운 정도로 결과가 부풀려집니다. 문서화되어 있으나 수정되지는 않았습니다
- **프로토타입은 공용 하네스로 실행된 적이 없습니다.** 저장된 평가 출력을 사용하므로, 기준선은 비교 대상 전부와 다른 코드로 측정되었습니다. `FUTURE_IMPROVEMENTS_KO.md`의 첫 번째 항목입니다
- **격리된 구간은 개발 중 1회 평가되었습니다.** 2026-08-11에 `scripts/ml_34_asof_bucket_audit.py`가 수행했으며, 이를 근거로 조정한 것은 없습니다
- **예측 구간이 없습니다.** v11은 점 예측만 산출합니다. 그 근거는 `FUTURE_IMPROVEMENTS_KO.md` §4에 있습니다
