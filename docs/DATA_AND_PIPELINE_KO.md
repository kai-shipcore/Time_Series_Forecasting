# 데이터와 파이프라인: 숫자의 출처와 매주 실행되는 것

**대상 독자:** 이 시스템을 운영하는 사람. 머신러닝 지식은 가정하지 않습니다. 로그 파일을 읽고
SSH를 쓰고 환경변수를 편집할 수 있다면 이 문서는 당신을 위한 것입니다.

**이 문서의 위치.** `OVERVIEW_KO.md`가 시스템의 목적을 설명합니다. `MODEL_KO.md`가 데이터가
준비된 이후에 일어나는 일을 설명합니다. 이 문서는 그 양옆의 모든 것을 다룹니다. 데이터가
어디에서 오는지, 주간 작업이 무엇을 하는지, 정상 동작 여부를 어떻게 확인하는지, 그리고 정상이
아닐 때 무엇을 할지입니다.

---

## 1. 주(week) 규약

**이것부터 읽으십시오. 서로 다른 버그를 두 번 일으켰고 여러 달 동안 문서마다 다르게 적혀
있었습니다.**

- 한 주는 **화요일부터 월요일까지 포함**입니다.
- 한 주는 **끝나는 월요일로 라벨링**됩니다. pandas 빈도는 `W-MON`입니다.
- 따라서 `2026-07-13`이라는 라벨은 7월 7일 화요일부터 7월 13일 월요일까지를 뜻합니다.

세 가지가 하나의 결정이며 함께 움직입니다.

1. 화요일부터 월요일까지의 기간(`src/clean.py`, `closed="right"`).
2. `W-MON` 라벨.
3. **화요일** cron.

주 규약을 바꾸면 cron 요일도 함께 바뀌어야 하며, 그렇지 않으면 파이프라인이 조용히 한 주를
잃습니다. 2026-08-06에 이 규약으로 되돌렸고, V1 비교는 그 되돌림에서 발생한 off-by-one을
2026-08-13까지 안고 있었습니다. 아무도 동시에 갱신하지 않았기 때문입니다.

**수요 숫자에 포함되는 것.** 네 가지 주문 유형 전부: `sales`, `preorder`, `ttm`,
`ttm_preorder`. 수요는 출고된 주가 아니라 **주문이 접수된** 주에 귀속됩니다. 이는 신규 출시
SKU에서 가장 문제가 되며, 출시 예약 주문이 짧은 이력을 지배할 수 있습니다.

---

## 2. 입력

| 출처 | 내용 | 단위 |
|---|---|---|
| `shipcore.fc_velocity_link_snapshot_forecast` | 주문 라인 테이블. 전체 주문 이력, 전 채널, 기간 제한 없음. **원천 데이터** | 주문 라인 1행 |
| `data/processed/sales_clean.parquet` | 위를 집계한 것. 주간 수집이 생성 | **SKU × 주 1행.** 완전 격자: 모든 SKU가 모든 주에 행을 가지며 판매가 없으면 0으로 채움 |
| `data/processed/sku_profiles.csv` | SKU별 세그먼트 라벨과 학습 시작일 | SKU 1행 |
| `ecommerce_data.coverland_inventory_by_warehouse` | 재고, 할당분, 백오더 | SKU × 창고 1행 |
| `shipcore.fc_container_items`와 `shipcore.fc_containers` 조인 | ETA가 있는 확정 및 초안 입고 | 컨테이너 라인 1행 |

재고와 컨테이너 테이블은 **Action List에서만 실시간으로** 읽습니다. 예측의 입력이 아닙니다.

**120일로 제한된 두 번째 속도 테이블이 존재합니다.** `shipcore.fc_velocity_link_snapshot`이며
Velocity UI 페이지 전용입니다. 예측은 제한이 없는 `..._forecast` 테이블을 사용합니다. 둘을
바꾸지 마십시오.

## 3. 출력

| 대상 | 내용 | 단위 |
|---|---|---|
| `shipcore.ml_forward_forecasts` | 현재의 13주 예측 | SKU × 미래 주 1행 |
| `shipcore.ml_forecast_history` | 제공된 모든 예측의 누적 | SKU × 대상 주 × 실행 1행 |
| `data/processed/ml_forward_forecasts.parquet` | 파일 사본, 읽기 폴백 | 동일 |
| `data/processed/ml_forecast_history.parquet` | 누적 이력의 파일 사본 | 동일 |
| `data/history_backups/` | 이력의 날짜별 사본, 최근 12개 보관 | 주간 |

두 `ml_` 테이블은 컬럼 정의를 공유하므로 서로 어긋날 수 없습니다. 키는
`(model_version, week_of, unique_id, ds)`이며, `week_of`는 해당 실행이 학습에 사용한 주,
`ds`는 예측 대상 주입니다. 모델 버전은 파일명이 아니라 항상 **컬럼**에 있으므로 여러 버전이
공존합니다.

**누적 이력은 재생성할 수 없는 유일한 산출물입니다.** 나머지는 전부 데이터베이스에서 다시
만들어집니다. 이력은 *결과를 알기 전에* 무엇을 예측했는지를 기록합니다. 오래된 모델을 오래된
컷오프에 다시 돌리면 백테스트가 되는데, 이는 더 약하고 다른 종류의 주장입니다. 그래서 테이블과
파일 양쪽에 기록하고 파일을 매주 백업합니다.

**동결됨, 더 이상 기록되지 않음.** `shipcore.fc_forward_forecasts`와
`shipcore.fc_forecast_history`는 은퇴한 statsforecast 트랙의 것입니다. 2026-08-13의 값에 멈춰
있습니다. 아무것도 갱신하지 않습니다. 현재 예측을 위해 읽지 마십시오.

## 4. 파이프라인

하나의 스크립트가 전체 순서를 수행합니다. **`scripts/ml_prepare_data.py`**.

```bash
.venv/bin/python scripts/ml_prepare_data.py --force --horizon 13
```

| 단계 | 하는 일 | 기록 대상 |
|---|---|---|
| **1/4  sync** | 주문 원천에서 속도 스냅샷 갱신 | `fc_velocity_link_snapshot_forecast` |
| **2/4  ingest + clean** | 주문을 가져와 주간 격자로 집계 | `sales_clean.parquet` |
| **3/4  profile** | 각 SKU를 버킷과 이력 길이로 분류 | `sku_profiles.csv` |
| **4/4  forecast** | LightGBM v11 실행, 예측과 이력 기록 | `ml_forward_forecasts`, `ml_forecast_history` |

**`--force`가 필요합니다.** 파이프라인이 기본적으로 운영 파일 덮어쓰기를 거부하기 때문이며,
이는 여기를 제외한 모든 곳에서 옳은 기본값입니다.

**`--snapshot live`는 사용되는 곳에서 결정적입니다.** 이것이 없으면 ML 스크립트는 기록된 평가
수치가 흔들리지 않도록 존재하는 고정 스냅샷을 기본값으로 씁니다. 동결된 스냅샷에 대한 주간
실행은 매주 같은 예측을 만들어내면서 정상 작동하는 것처럼 보입니다.

**지평의 하한은 13이며** UI 옵션과 엔드포인트 시그니처(`Query(default=13, ge=13, le=104)`)에서
강제되지만 **스크립트에서는 강제되지 않습니다.** 각 실행은 해당 학습 주의 저장된 예측을
대체하므로, 더 짧은 실행은 완전한 스냅샷을 덮어씁니다.

### 4.1 실패한 실행은 안전하며, 이것이 유용한 성질입니다

모든 산출물은 `/tmp`가 아니라 `data/processed/` **옆의** 스테이징 디렉터리에 기록되고, 예측이
성공한 뒤에야 `os.replace`로 제자리에 이동합니다. `os.replace`는 같은 파일시스템 안에서
원자적이며, 그래서 스테이징 디렉터리가 형제 디렉터리여야 합니다.

따라서 크래시, 실패한 단계, 끊어진 SSH 세션은 지난주 파일을 그대로 두고 계속 서비스되게 합니다.
결과는 한 주 지난 예측이지, 세그먼테이션은 어느 주를 설명하고 판매는 다른 주를 설명하는 반쯤
갱신된 상태가 **아닙니다.** 스크립트는 0이 아닌 코드로 종료하므로 문제가 생긴 화요일에 cron이
메일을 보냅니다.

**이것이 만들어내는 실패 양상.** 오래된 예측은 외부에서 보면 정상인 것과 구분되지 않습니다.
페이지가 로드되는지만 보지 말고 Action List의 `trained_through`를 달력과 대조하십시오.

## 5. 주간 실행

서버에서 `coverland` 사용자로 실행되는 cron 항목 하나입니다.

```
0 10 * * 2 cd /opt/coverland-forecast-api && scripts/run_forecast_cron.sh >> logs/forecast_cron.log 2>&1
```

**화요일(요일 2)이며 이것은 결정적입니다.** 한 주는 끝나는 월요일로 라벨링되므로, 월요일 L로
라벨링된 주는 월요일 L 하루 종일 아직 열려 있습니다. 월요일 실행은 *직전* 월요일에 닫힌 주만
쓸 수 있어 모든 예측이 필요 이상으로 한 주 낡게 됩니다. 화요일 실행은 몇 시간 전에 닫힌 주를
가져옵니다.

**설정 당시 10:00 UTC는 태평양 시간 오전 3시였습니다.** 서버는 UTC를 유지하므로 태평양 기준
벽시계 시각은 서머타임 전환마다 한 시간씩 밀립니다. 그 시간대가 중요하다면 연 2회 조정하십시오.

스크립트는 세 가지를 합니다.

1. **파이프라인**, `ml_prepare_data.py --force`.
2. **준비 상태 확인.** `/health`를 호출해 `ready: true`를 확인합니다.
3. **이력 백업.** 누적 이력을 `data/history_backups/`로 복사하며 최근 12개를 보관합니다.

**예전에 여기 있던 것과 그것을 알아야 하는 이유.** 2026-08-13까지 cron은 statsforecast
파이프라인을 **먼저** 실행했습니다. 그것만이 `sales_clean.parquet`을 만들었기 때문입니다.
운영 환경에서 파일 두 개를 얻기 위해 매주 전체 교차검증과 모델 선택을 돌리고 있었습니다. 이는
구 트랙 삭제를 최악의 방식으로 위험하게 만들었습니다. 오류를 내지 않았을 것이기 때문입니다.
예측은 계속 제공되면서 그저 움직이지 않게 되었을 것입니다. 수정에는 새 코드가 필요 없었고,
이미 몇 주 동안 ML 전용 순서를 수행해온 스크립트로 cron을 돌리기만 하면 되었습니다.

## 6. 함부로 움직여서는 안 되는 두 개의 고정값

| 고정값 | 위치 | 고정하는 것 |
|---|---|---|
| `ML_FINAL_TEST_CUTOFF` | `config.py:44`, 현재 `2026-05-04` | 각 평가 구간이 포함하는 주 |
| `ML_DATA_SNAPSHOT` | `config.py:67`, 현재 `2026-08-03-v2` | 그 주 안의 값 |

기록된 결과가 재현되려면 둘 다 필요합니다. 주간 갱신이 늦게 등록되는 주문을 반영해 최근 실적을
수정하기 때문입니다. **둘 중 하나라도 앞으로 옮기면 프로젝트의 모든 수치가 재기준화됩니다.**
하나를 옮기고 다른 하나도 따라왔으리라 가정하지 마십시오.

ML 트랙은 평가 입력을 `data/processed/`가 아니라 `ML_DATA_SNAPSHOT`이 지정하는 스냅샷에서
읽으며, 그래서 주간 갱신이 기록된 결과를 움직일 수 없습니다.

## 7. 정상 동작 여부 확인

### 한 줄 점검

```bash
curl -s http://144.24.40.252:8000/health | python3 -m json.tool
```

`/health`는 의도적으로 토큰 검사 **바깥**에 있으므로 토큰이 틀려도 응답합니다.

| 필드 | 의미 |
|---|---|
| `ready` | `true`면 필요한 데이터 파일이 전부 있음. `false`면 서비스는 살아 있으나 제공할 것이 없고 모든 계획 페이지가 500을 반환 |
| `missing_required` | `ready`가 false일 때 누락된 파일 |
| `commit` | **실제로 서비스 중인 리비전.** `main`의 최신 커밋과 대조 |

**`commit`은 사람들이 잊는 필드입니다.** "서비스가 이 디렉터리에서 실행 중이다"는 이전 배포에서
남은 프로세스에도 해당됩니다. 배포되지 않은 푸시와 포트를 잡지 못한 배포 둘 다 여기서 커밋
불일치로 드러나며, 이 필드가 생기기 전에는 둘 다 보이지 않았습니다.

`ready`를 503이 아니라 본문으로 보고하는 것은 의도입니다. "서버 없음"과 "데이터 없는 서버"는
해결책이 다른 별개의 문제입니다.

### 이미 감시하고 있는 것

- **시간별 GitHub Actions 워크플로**가 외부 접근성을 확인하고 토큰이 여전히 강제되는지
  점검합니다. 토큰 보호 엔드포인트에서 `200`이 나오면 그곳에서는 **실패**입니다. API가
  인터넷에 열려 있다는 뜻이기 때문입니다.
- **주간 cron**이 실패 시 메일을 보냅니다.
- **계획 페이지**가 서비스 상태를 표시하고 서버에 도달할 수 없을 때 이를 보고합니다.

### API 모듈을 변경한 뒤

```bash
.venv/bin/python scripts/check_route_parity.py --probe
```

API가 여전히 제공해야 할 라우트를 제공하는지 확인합니다. 데이터베이스도 네트워크도 필요
없습니다. 이것이 존재하는 이유는 뻔한 방식의 검사가 동작하지 않기 때문입니다. FastAPI는 포함된
라우터를 단일 불투명 객체로 저장하므로 라우트 개수를 비교하는 것은 아무것도 비교하지 않습니다.
이 스크립트는 라우터 트리를 순회하고 앱의 실제 매칭 로직을 구동하며, 매번 **음성 대조군**을
실행하므로 검사가 눈이 멀었을 때 통과하는 대신 그렇다고 말합니다.

### 무엇이든 푸시하기 전에

```bash
.venv/bin/python scripts/verify_repo.py          # 8개 정적 검사
.venv/bin/python scripts/smoke_planning_api.py   # 모든 계획 엔드포인트, 인프로세스
```

스모크 테스트가 "Action List와 Forecast Validation 페이지가 동작하는가"에 답하는 검사입니다.
정적 검사가 찾지 못한 실제 버그를 찾아냈습니다. 컬럼 이름 변경으로
`forecast_snapshot_date()`가 더 이상 존재하지 않는 컬럼을 요구하게 되면서 두 페이지 모두
2026-08-12부터 500을 반환하고 있었습니다.

## 8. 문제가 생겼을 때

| 증상 | 유력한 원인 | 먼저 확인할 것 |
|---|---|---|
| 페이지가 예측 서버에 도달할 수 없다고 표시 | 서비스 다운, 또는 `AI_SERVICE_URL`이 잘못됨 | **로컬 서버가 실행되지 않는 기기에서** `curl /health` |
| `/health`는 응답하나 `ready`가 false | cron이 실행되지 않았거나 실패 | `crontab -l \| grep run_forecast_cron`, 그다음 `logs/forecast_cron.log` |
| 모든 계획 페이지가 500 | 위와 동일. 제공할 데이터 없음 | `/health`의 `missing_required` |
| 예측이 주마다 움직이지 않음 | cron이 커밋 전에 실패. 실패한 실행은 설계상 지난주 파일을 남기므로 외부에서는 정상과 동일하게 보임 | `logs/forecast_cron.log`, 그리고 `trained_through`를 달력과 대조 |
| `commit`이 `main` 최신이 아님 | 배포되지 않은 푸시, 또는 포트를 잡고 있는 낡은 프로세스 | 해당 푸시의 GitHub Actions 실행 |
| Action List에 "SAMPLE inventory data" 표시 | 데이터베이스 자격증명이 잘못됨 | `DB_*`와 `COMMERCE_DB_*`가 **둘 다** 설정되어야 함. 일부만 설정되면 조용히 성능 저하 |

**이 프로젝트가 두 번 저지른 진단 실수.** 개발 기기가 서버와 통신하는 것처럼 보였지만 아니었습니다.
Next.js 앱은 설정된 서버가 응답하지 않을 때 *로컬* 예측 서비스를 시작하는 폴백이 있어서, 잘못
설정된 `AI_SERVICE_URL`이 다른 무언가가 응답하는 동안 정상처럼 보입니다. **이를 결정적으로
가리는 검사는 로컬 서버가 없는 기기에서의 `curl`입니다.** 마지막이 아니라 먼저 하십시오.

**관련하여:** `Commerce_Integration`에는 `.env`와 `.env.local`이 모두 있고 **`.env.local`이
이깁니다.** 이는 프로젝트 관례가 아니라 Next.js의 우선순위입니다. 두 사람이 각자의 기기에서
`.env`의 `AI_SERVICE_URL`을 수정했는데 어느 쪽도 아무 효과가 없었던 적이 있습니다. 편집하기 전에
어느 파일이 값을 공급하는지 확인하고, 편집 후에는 개발 서버를 재시작하십시오. 환경변수는 시작
시점에 읽힙니다.

## 9. 배포

**코드는 `main`에 푸시하면 배포됩니다.** GitHub Actions로 SSH를 통해 rsync한 뒤
`coverland-forecast-api` systemd 유닛을 재시작합니다. 수동 단계는 없습니다.

**데이터는 배포되지 않습니다.** 배포는 `data/`, `outputs/`, `logs/`를 제외하며, `rsync --delete`
하에서 이는 "업로드하지 않음"과 "파괴하지 않음"을 동시에 뜻합니다. 서버의 데이터는 cron이
소유하고 배포는 손대기를 거부합니다. 이 제외가 없으면 모든 배포가 서버 데이터를 지우고 다음
화요일까지 API가 500을 반환하게 만듭니다.

이 제외 목록은 `.gitignore`를 다시 적은 것이 **아니며**, 그렇게 읽는 것은 이 프로젝트 문서가
예전에 저질렀던 실수입니다. `data/` 아래 일부 경로는 의도적으로 추적됩니다. 규칙은 git에 무엇이
있느냐가 아니라 **소유권**에 관한 것입니다.

**두 저장소가 함께 바뀔 때는 순서가 중요합니다.** **Commerce를 먼저, 또는 둘을 동시에** 배포하십시오.
Python 쪽이 구 페이지가 호출하는 엔드포인트를 내리므로, API가 먼저 나가면 아직 살아 있는 페이지가
오류를 냅니다.

배포 후 `/health`의 `commit`이 `main` 최신과 일치하는지 확인하십시오.

`DEPLOYMENT.md`가 서버 설정, 시크릿, 런북의 전체 참조이며 이 요약보다 상세합니다.

`outputs/reports/` 아래의 리포트입니다.

## 11. 유지보수 일정

| 시점 | 작업 |
|---|---|
| 매주, 자동 | 화요일 cron. cron이 실패 메일을 보내면 로그 확인 |
| 배포할 때마다 | `/health`의 `commit`이 `main` 최신과 일치하는지 |
| API 코드 변경 후 | `scripts/check_route_parity.py --probe` |
| **운영 모델 버전이 바뀔 때** | **`outputs/reports/ml_accuracy.csv` 재생성**, `scripts/ml_accuracy_report.py`. 아래 경고 참조 |
| 연 2회 | cron의 UTC 시각이 서머타임 전환마다 태평양 기준 한 시간씩 밀림 |
| 의존성 변경 시 | PyPI가 아니라 **배포 호스트**에서 `pip freeze`로 고정 |

**정확도 리포트에는 아무도 적어두지 않은 갱신 조건이 있습니다.** 스크립트의 docstring은 "운영
모델 버전이 바뀔 때" 갱신하라고 되어 있습니다. 이는 불완전합니다. **모집단**이 바뀔 때도 갱신해야
하며, 프로파일링이나 임계값 변경이 바로 그런 경우입니다. 디스크의 파일은 2026-07-30자이고 그런
변경 세 건보다 앞서므로, Forecast Validation 화면은 현재 낡은 수치를 보여주고 있습니다.
`SCREENS_KO.md` 3.7절 참조.

**의존성 고정에 관하여.** `requirements.txt`의 모든 버전은 정확히 고정되어 있습니다. 머신러닝
관련 다섯 개는 결과를 소수점 셋째 자리로 비교하기 때문이며, 이는 고정하지 않은 솔버 업데이트가
유발할 수 있는 편차보다 미세합니다. 서비스 쪽 고정은 나중에 추가되었는데, 아무도 이름을 댈 수
없는 FastAPI 버전에서 라우트 등록에 검증 불가능한 변경이 일어난 뒤였습니다. 두 그룹 모두
완화하지 마십시오.

## 12. 함께여야만 참인 것들

집합으로서만 의미가 있는 제약입니다. 하나를 나머지 없이 바꾸면 무언가가 조용히 깨집니다.

- **화요일 cron, `W-MON` 라벨, 화요일부터 월요일까지의 기간.** 하나의 결정입니다.
- **`ML_FINAL_TEST_CUTOFF`와 `ML_DATA_SNAPSHOT`.** 재현성에 둘 다 필요합니다.
- **`ml_prepare_data.py`와 주간 cron.** cron의 유일한 임무는 이것을 호출하는 것이며, Action
  List의 Run Forecast 버튼이 호출하는 것도 같은 스크립트입니다. 하나의 스크립트, 두 개의 트리거,
  순서의 두 번째 사본 없음. 이는 의도입니다. 예전에는 둘이 달랐고 그 차이는 어느 화면에서도
  보이지 않았습니다.
- **양쪽의 `FORECAST_API_TOKEN`.** Python 서비스와 Next.js 앱이 일치해야 하며, 아니면 `/health`를
  제외한 모든 요청이 401을 반환합니다.
- **`run-forecast.tsx`의 진행 바와 `ml_prepare_data.py`의 표준 출력.** 컴포넌트가 스크립트 출력에서
  `Step N/4`를 정규식으로 찾습니다. 그 접두사를 바꾸면 진행 바가 조용히 깨집니다. 이 계약은 코드
  어디에도 명시되어 있지 않습니다.
